A scanner alert is an observation.
A penetration-test finding is a conclusion that still needs evidence and context.
That gap is where this project concentrates its engineering.
In the recorded Juice Shop example, five tools produced 480 alerts.
The pipeline assembled 69 finding groups.
Those are not 69 independently demonstrated exploits, and the reduction is not proof of equivalent time saved.
It is a smaller, structured set that a reviewer can inspect.
We will follow six observations into one CORS group, then ask the harder questions: who decides what runs, what the model contributes, what happens when it is wrong, and what the audit trail can actually prove.
First, separate collecting scanner output from processing it.
The evidence was recorded against deliberately vulnerable lab targets.
Preflight checks the declared target and Docker environment before the permitted lab workflow proceeds.
The repeatable demo does not launch fresh scanners.
It reads those recorded files.
ZAP, Nuclei and Nikto contribute web observations; image and dependency tools contribute a different kind of evidence.
Adapters translate their formats into a common Finding representation while retaining source identifiers.
Real model calls may still happen during this replay.
That makes the experiment reproducible at the input layer, not guaranteed identical at every model output.
In the diagram, recorded acquisition and current processing are different lanes.
A line between them is data provenance, not a live attack.
The agent is allowed to choose within a catalog, not invent executable commands.
Its response contains an action identifier, profile, target, evidence identifiers and a rationale.
A parser validates the structure.
The policy gate checks the allowed combination, known evidence, budgets and whether that action has already been attempted.
A structurally valid answer can still be denied.
An unknown evidence identifier does not become real because a model cited it.
Refusal, malformed output and provider failure have explicit fallback paths instead of blind re-prompting.
Crucially, the default runner in this POC records admitted steps as not executed.
This demonstrates constrained selection and auditable receipts; it is not proof of a closed-loop autonomous scanner.
Following a reference to evidence also does not prove the reasoning is correct.
The boundary limits authority, not the possibility of a bad judgment.
Two tools rarely describe the same issue in exactly the same words.
The grouping code therefore models equivalence rather than matching titles.
For site-wide checks, the key uses the normalized origin, weakness family and rule family.
For input-sensitive weaknesses, method and parameter can distinguish separate findings.
Network groups retain host and port.
A shared CWE alone must not collapse unrelated fixes.
In our example, six Nikto and ZAP observations map to the CORS family and one stable group.
Source finding identifiers and affected locations remain available.
The merge reduces repetition without pretending that the original observations never existed.
These are explicit grouping rules and assumptions, not an AI discovery of the true root cause.
They deserve review.
And a wildcard CORS header may be intentional on public resources: the grouped observation still needs a contextual security judgment.
The report pipeline does not delegate everything to the language model.
Code applies taxonomy and remediation rules.
For dependency groups with published vectors, it can compute a score from the highest available advisory vector without asking the model to invent one.
Where a model proposal is needed, the model supplies a CVSS vector and rationale, not the final numeric score.
The vector is validated and the library performs the calculation.
Invalid output or a provider error can leave the finding explicitly unscored.
Correct arithmetic does not prove the vector's assumptions are correct.
Our CORS report contains a proposed 4.3 score; that is not a demonstrated exploit or a complete business-risk assessment.
The separate verdict stage uses a closed set: true positive, noise, or needs human review.
Unusable replies fall back to needs-human.
A noise label retains the finding in the report but removes it from normal issue filing.
That is a consequential decision, not just a cosmetic badge.
The Juice Shop snapshot reports 92 percent precision across actionable groups.
But most of that set consists of dependency groups.
Web-only precision is 55 percent before model filtering and 86 percent afterward.
Those are different views of the same sample, not interchangeable measures of overall accuracy.
Recall asks a different question.
The recorded profile found seven of seven weaknesses classified as in scope, but seven of eleven known weaknesses overall.
One hundred percent in-scope recall is therefore compatible with 64 percent overall recall.
Now examine WebGoat.
Its sample reports perfect precision, yet the model labelled four real findings as noise.
Removing true findings can leave the precision of the remaining set unchanged.
A cleaner-looking queue is not automatically a safer result.
Ground truth is provisional, and different targets behave differently.
The project makes these disagreements measurable.
That is a stronger basis for engineering discussion than presenting one flattering percentage as proof that the AI is trustworthy.
Findings must remain comparable across runs.
The diff code uses a fingerprint derived from the target and grouping key.
It distinguishes new, still-open, fixed and not-retested results.
If a finding disappears because its scanner or relevant profile did not run again, the system must not celebrate a fix.
It becomes not retested.
A finding still present under a different model label must not silently turn into a fixed issue either.
These checks prevent specific false conclusions.
Even a result labelled fixed by this comparison remains a claim about the compared reports and their coverage, not independent proof that a developer repaired the underlying application.
The reviewer still needs appropriate retest evidence.
The audit trail ties decisions and receipts to a run and provider label.
The verifier checks sequence, linked hashes, consistent identity and a complete run ending.
That lets us inspect whether the saved records are internally consistent and whether an incomplete log has been presented as finished.
A local hash chain is not a signature, immutable storage, or proof that a finding is true.
Someone able to rewrite the entire chain could recompute it unless an external trusted anchor is added.
That is a boundary of this implementation, not a reason to discard its traceability.
The deliverable is a structured, inspectable chain from recorded evidence through bounded model involvement to reports and optional tracking.
Normalization, grouping, admission, scoring, fallback, accuracy and change detection are the engineering—not just the model prompt.
The next evaluation is practical: review the grouping assumptions, validate the ground truth, inspect false suppressions, and measure analyst effort against a manual baseline.
This POC does not replace a penetration test.
It provides a controlled way to investigate how much of the scanner-to-report workflow can be made repeatable and reviewable.
