01 — WHAT DOES FIXED ACTUALLY PROVE?

An AWS compliance finding tells us something may be wrong. It does not tell us who may change it, which exact change is approved, or whether the result has been independently verified. AWSOps, the backend of the Defence Factory prototype, is built around that gap. The interesting part is not a model generating an AWS command. It is the boundary between evidence, an exact proposed action, a genuine human decision, and an outcome we can defend. A finding is not authority. Approval is not execution. A successful operation is not fresh compliance evidence. We will follow one disposable S3 canary. This walkthrough is synthetic and grounded in repository code, not a recording of a successful AWS change. Keep four questions separate: what ran, what the provider observed, what compliance evaluated, and how fresh that evaluation is. Missing answers should stay unknown.

02 — IMPORT DATA, NEVER AUTHORITY

The shared contract distinguishes findings, controls, target registrations, batches, decisions, runs, and evidence. These records make different claims. An envelope has a schema version, a kind, and a record. Unknown fields are rejected. The bounded synthetic intake limits bytes and rows, rejects duplicate keys and conflicting identities, and keeps imported content inert. Its supported accounts are mock aliases. Our public resource alias represents a disposable canary, never a private bucket name. Even a structurally valid finding remains an imported assertion. It cannot attest an AWS observation. A target registration is a public projection, not an IAM trust relationship. A private backend must separately resolve the approved identity and resource. The companion Agent Core Two interface consumes evidence; its presence does not prove a live integrated deployment. The offline planner and the canary adapter are separate paths. The same public alias connects our explanation, but imported evidence does not become permission or a trusted provider read by moving across the diagram.

03 — FREEZE PRECISELY WHAT CAN CHANGE

Approval is meaningful only when it names an exact operation. Here we enter the canary adapter's separate preparation path, using a synthetic observation. The batch binds one target, its revision and evidence digest, the registry version, mode, frozen time, and expiry. Its capability is require TLS; its expected change is deny insecure transport. The scope digest covers the complete batch with that digest field omitted. Canonical object keys are sorted; target array order is retained. Change the target or evidence revision and the seal no longer matches. The adapter also checks the private binding and current evidence before execution. Expired preparation or changed provider state cannot silently inherit the earlier approval. The canary reuses a maximum five minute preparation window and a sixty second observation age check. These limits do not turn a hash into authentication. The older single finding Frozen Scope is a different type, not this batch schema. The application additionally binds the principal, source revision, fixed setup actions, cost bound, and any conditional cleanup.

04 — ONE DURABLE DECISION, BEFORE DISPATCH

The decision must come from a trusted authenticated backend. Possessing the digest, typing a phrase, or importing a document that says approve does not identify an authorized person. Inside the canary adapter, an immediate database transaction selects the saved batch and checks the principal, binding, scope, mode, and expiry. It commits the winning decision and initial run together, before any provider operation. Approve Once and Reject both consume that slot. A competing choice cannot replace the winner. In this illustrative race, Reject wins: zero provider writes. The application also claims a verified approval packet once; replay of the same packet reopens the same result instead of creating another run. Now the important current boundary: the legacy native store records rejected or approve blocked, with dispatch disabled. The ordinary live canary operator refuses approval before constructing a provider because its trusted human approval binding is missing. The injected test verifier authorizes only a mock provider. Our approved branch is a synthetic explanation of the implementation, not a real owner's decision.

05 — FOUR FIXED MUTATIONS, NO ARBITRARY AGENT

The canary is deliberately narrow: a new, empty, task owned lab bucket and a fixed TLS only policy. The provider checks the selected personal lab profile and Region, then compares a fresh non root identity with the private expected account. A preexisting bucket is not eligible. The fixed setup sequence creates the bucket, writes task tags, enables all four public access block flags, and applies the reviewed transport policy. Public access blocking and denying non TLS transport are different protections. This is not encryption at rest remediation. The policy denies S3 actions when secure transport is false. There is no model accessible arbitrary AWS method in this path. Before the policy write, fresh reads require acknowledged task creation, exact tags, an empty object listing, no versions or delete markers, the expected public block, and no existing policy. Each mutation has a durable ledger row. Intent becomes calling immediately before the SDK boundary, and an acknowledged call becomes ACK. A merged IAM proposal alone does not prove its role is installed.

06 — UNKNOWN MEANS RECONCILE, NOT RETRY

Suppose the policy request crosses the SDK boundary, but its response disappears. That is not proof AWS rejected the request. The operation stays calling and execution stays unknown. Automatically replaying it would turn uncertainty into another mutation. The provider disables automatic mutation retries, and reconciliation reads the same run instead of minting a fresh batch. If every setup row is acknowledged, reconciliation can recover execution succeeded after a crash before the final result save. A calling row remains uncertain. The exported write count counts conservative SDK mutation attempts, not independently proven cloud changes. A known pre call refusal adds no attempted write. In our mock example, those attempts belong in simulated writes and real writes remains zero. Cleanup is not an escape hatch. One authenticated packet may cover both setup and exact conditional cleanup, but omitting cleanup grants no deletion authority. Fresh ownership, emptiness, operation state, and cleanup expiry still matter. An uncertain operation blocks destructive cleanup; a task tag or time to live does not schedule deletion.

07 — MATCH IS ONE LANE, NOT THE VERDICT

Even when the SDK sequence succeeds, the result is not automatically verified. The adapter reads provider state independently and checks the intended transport policy. A matching policy proves only what that readback observed. It does not trigger or prove a fresh AWS Config evaluation. Our synthetic successful branch therefore has execution succeeded and provider readback match, while compliance stays unknown and freshness stays not verified. The run remains needs review. These are real schema values, not four names for the same green light. The shared contract requires the selected targets and independent evidence before verified can be justified; this adapter deliberately does not make that claim. The evidence also separates the source revision from an observed hosted version. Here hosted version is null. The schema's mock version suffix alone is not a deployment receipt. A private durable ledger preserves recovery information, but a privileged host writer is still a trust assumption; a digest or local hash chain is not an independent tamper proof signature.

08 — SOURCE, SIMULATION, LIVE READ, PENDING PROOF

The repository contains concrete engineering: bounded intake, shared contracts, exact scope binding, durable decisions, a fixed provider, uncertainty handling, and evidence that refuses to overclaim. The source tests assert approval, rejection, drift, expiry, replay exclusion, and uncertain acknowledgement behavior with fake providers. That is synthetic proof, not a live owner approval. There is also accepted historical AWS Config read proof from October eleventh. It establishes bounded account local acquisition, not evaluation freshness or remediation. The later transfer record still retains ledger provenance and initialization, exact deployed pins, genuine normal login Reject, and provider and compliance verification as pending outcomes. The old execution issue closed as transferred, not completed product acceptance. We checked the source at the reviewed revision; this film performed no AWS calls. The proposition is controlled change with inspectable evidence. The next useful test is to close the exact remaining live acceptance gap, not add another model or turn missing evidence green. What was approved, what ran, and what the evidence proves must remain separate questions.
